# Q7. Important LLM-Related Concepts (Answers)

---

## Question 7.1

What problem does each of the following solve: Prompt Engineering, RAG, Fine-Tuning, AI Agents?

---

**Answer:**

[*] Prompt Engineering → LLM outputs are inconsistent or low quality: crafting better inputs gets better outputs.
[*] RAG → LLM has a knowledge cutoff / no access to private data: retrieve relevant documents at query time and ground the answer in real sources.
[*] Fine-Tuning → LLM gives generic responses not suited to a specific domain or style: train the model further on your specific data.
[*] AI Agents → LLM can only generate text but cannot take actions: give the LLM tools and an action loop so it can plan, call APIs, and complete multi-step tasks.
[ ] RAG retrains the LLM on new data every time a question is asked.
[ ] Fine-Tuning is the cheapest solution for adding up-to-date information.

---

## Question 7.2

Compare zero-shot, few-shot, and chain-of-thought prompting. When would you use each?

---

**Answer:**

[*] Zero-shot: ask directly with no examples. Use when the task is clear and the LLM should already handle it well. Simple and fast.
[*] Few-shot: provide 2–5 input/output examples before the real question so the LLM learns the desired pattern. Use when you need a specific output format or style.
[*] Chain-of-thought (CoT): add "Think step by step" or provide step-by-step examples. Use for math, logic, multi-step reasoning — significantly improves accuracy on hard problems.
[*] System prompts: set the LLM's role and behavior for the whole conversation. Use to define persona, constraints, tone, and output style.
[ ] Zero-shot is more accurate than few-shot because providing examples confuses the model.
[ ] Chain-of-thought only helps with arithmetic, not with logic or code.

## Question 7.3

Describe the two phases of RAG (indexing and query). What happens at each step?

---

**Answer:**

[*] Indexing phase (offline, done once): collect documents → split into chunks (e.g., 500 tokens each) → embed each chunk into a vector → store vectors in a vector database.
[*] Query phase (per question): embed the user question → search the vector database for similar chunks → combine retrieved chunks + question as context → send to LLM → generate final answer.
[*] Key benefit: the LLM's answer is grounded in retrieved real documents, reducing hallucination and enabling use of private/up-to-date data without retraining.
[ ] In RAG, the user's question is directly sent to the LLM with no retrieval step.
[ ] RAG trains the LLM on new documents every time a query is made.

## Question 7.4

When should you choose RAG vs Fine-Tuning? Give two scenarios for each.

---

**Answer:**

[*] Use RAG when: data changes frequently (easy to update the vector DB); you need up-to-date information (just update documents); hallucination reduction matters (answers grounded in sources); cost must be low (no GPU training needed).
[*] Use Fine-Tuning when: you need a specific output style or format the model doesn't naturally use; domain expertise must be deeply embedded (not just retrieved); data is stable and won't change often; you want the model to "speak" in your company's voice.
[*] In practice, many production systems use both: a fine-tuned model + RAG for retrieval.
[ ] Fine-Tuning should always be the first choice because it produces better results than RAG.
[ ] RAG cannot be combined with Fine-Tuning — they are mutually exclusive approaches.

## Question 7.5

What is an AI Agent, and what does the "agent loop" look like?

---

**Answer:**

[*] An AI Agent = an LLM that can plan, decide, and take actions — not just generate text. The LLM is the "brain" deciding which tools to call and when to stop.
[*] Agent loop: User Request → LLM thinks → Decides action → Executes tool → Observes result → LLM thinks again → (repeat until done) → Final Answer.
[*] Example: "What's the weather in Cincinnati and should I bring an umbrella?" → Agent calls weather_api → gets rain forecast → generates natural language response. Regular LLM would just describe how to check weather.
[*] Agentic frameworks (LangChain, LangGraph, CrewAI, AutoGen, Claude Code) provide the orchestration layer for this loop.
[ ] An AI Agent generates all actions in one shot, without looping or observing results.
[ ] The agent itself executes code — the LLM runs the tools directly.

## Question 7.6

What is function calling (tool use)? Who executes the function — the LLM or the application?

---

**Answer:**

[*] Function calling: the LLM outputs a structured JSON object describing what function to call and with what arguments — it does NOT execute code itself.
[*] Your application receives the JSON, executes the function, and sends the result back to the LLM for a final natural language response.
[*] Example: "15% tip on $84.50?" → LLM outputs {function: "calculate_tip", arguments: {bill: 84.50, tip_pct: 15}} → app executes → returns $12.68 → LLM responds "A 15% tip would be $12.68."
[*] Workflow: define tools (JSON schema) → LLM decides whether to call a tool → app executes → result returned → LLM generates final response.
[ ] The LLM directly executes Python or JavaScript code during function calling.
[ ] Function calling requires the LLM to be fine-tuned on every specific function before use.

## Question 7.7

What is MCP (Model Context Protocol)? What problem does it solve, and what does each component (Host, Client, Server) do?

---

**Answer:**

[*] MCP = Model Context Protocol — an open standard by Anthropic for connecting LLMs to external data sources and tools. Analogy: "USB for AI."
[*] Problem it solves: before MCP, each AI app builds custom integrations for every tool (N × M problem). With MCP, tools implement the standard once and all AI apps can use them (N + M problem).
[*] Host: the AI application (Claude Desktop, VS Code, IDE) that uses MCP.
[*] Client: manages the connection protocol (1:1 with one server).
[*] Server: exposes tools, resources, and prompts via MCP (e.g., filesystem, GitHub, Slack, databases).
[ ] MCP is a Transformer architecture variant for multi-modal inputs.
[ ] MCP is proprietary to Claude and cannot be used with other LLMs.

---

## Question 7.8

What three types of capabilities can an MCP server provide? Give one example for each.

---

**Answer:**

[*] Tools: functions the LLM can call. Example: `search_database`, `send_email`, `greet(name)`, `add(a, b)`.
[*] Resources: data the LLM can read. Example: file contents, database records, calendar entries.
[*] Prompts: pre-defined prompt templates. Example: "summarize this code", "review this PR."
[*] Once an MCP server is running, any MCP-compatible host (like Claude Desktop) automatically discovers and can use all exposed tools, resources, and prompts.
[ ] MCP servers only provide Tools — Resources and Prompts require separate protocols.
[ ] An MCP server must be restarted every time a new tool is added.

## Question 7.9

What is an embedding, and how does a vector database enable semantic search? How is it different from a traditional keyword search?

---

**Answer:**

[*] Embedding: converting text (or images, audio) into a dense vector (list of numbers) that captures its meaning. Similar meanings → similar vectors → close in vector space.
[*] Example: "king" → [0.21, 0.83, -0.45, ...]; "queen" → [0.19, 0.81, -0.43, ...] (close); "apple" → [0.72, -0.31, 0.55, ...] (far).
[*] Vector database stores embeddings and enables similarity search: "Find docs closest to embed('mobile app framework')" → returns Flutter docs, React Native docs, etc.
[*] Traditional DB: SELECT * FROM docs WHERE text LIKE '%Flutter%' → keyword match only, misses synonyms and related concepts. Vector DB finds semantically similar content even if different words are used.
[ ] Embeddings convert text to images for visual comparison.
[ ] A vector database uses SQL WHERE clauses to find similar documents.

## Question 7.10

Draw the complete pipeline for an AI-powered customer support system using all the concepts from this lecture.

---

**Answer:**

[*] System Prompt (Prompt Engineering): defines tone, policies, escalation rules for the support chatbot.
[*] RAG: retrieves relevant support articles and past tickets from a vector database when a customer asks a question.
[*] Fine-Tuning: model trained on 10,000 past support conversations for company-specific style and terminology.
[*] Tool Use / MCP: can look up order status, process refunds, create tickets via MCP servers connecting to backend systems.
[*] Agent Loop: chatbot autonomously handles multi-step requests — check order → find issue → process refund → confirm — looping until the task is complete.
[*] Pipeline: User Question → Prompt Engineering → RAG retrieval → Fine-tuned LLM → Agent / Tool Use → Final Answer.
[ ] A customer support AI only needs prompt engineering — RAG and fine-tuning are unnecessary.
[ ] MCP cannot be used with RAG in the same system.
